# 2.1 — Требования к учебному ИИ-сервису сегментации глиомы

## 1. Назначение документа

Документ фиксирует диагностические и функциональные требования к учебному ИИ-сервису для автоматической сегментации опухоли головного мозга по МРТ-исследованиям. Документ используется как результат практической работы 2.1 и как основа для архитектурного описания в `docs/2.2_architecture.md`.

## 2. Цель сервиса

Цель сервиса — предоставить учебный прототип медицинского ИИ-сервиса, который принимает МРТ-исследование головного мозга, запускает модель сегментации глиомы и возвращает врачу визуальные и численные результаты анализа.

Диагностический результат сервиса:

- многоклассовая маска сегментации опухолевых областей;
- численные метрики качества сегментации при наличии эталонной маски;
- PNG-визуализации выбранных срезов;
- PNG-визуализации наложения предсказанной маски на исходную МРТ-модальность;
- DICOM-экспорт выбранной модальности для передачи в Orthanc/PACS-контур.

Сервис не является медицинским изделием и предназначен для учебной демонстрации архитектуры ИИ-сервиса, обработки медицинских изображений и интеграции с элементами радиологической информационной системы.

## 3. Медицинский сценарий

Сценарий использования: врач-рентгенолог или оператор загружает МРТ-исследование пациента, представленное четырьмя модальностями `t1`, `t1ce`, `t2`, `flair`. Сервис выполняет автоматическую сегментацию опухоли головного мозга и формирует результат, который может быть просмотрен в веб-интерфейсе или экспортирован во внешний DICOM/PACS-контур.

Основная диагностическая задача — семантическая многоклассовая сегментация глиомы по 3D МРТ-данным.

Целевые классы маски:

| Класс | Описание |
| --- | --- |
| `0` | Фон / отсутствие опухолевой ткани |
| `1` | Некротическое и неконтрастирующее ядро опухоли |
| `2` | Перитуморальный отёк |
| `3` | Контрастирующая опухоль; соответствует исходной метке `4` в BraTS, приведённой к индексу `3` для обучения |

## 4. Роли пользователей

### 4.1. Врач-рентгенолог

Врач-рентгенолог является основным пользователем результата ИИ-сервиса.

Операции:

- авторизоваться в системе;
- просматривать список доступных исследований;
- открывать карточку исследования;
- просматривать статус обработки;
- просматривать PNG-срезы исходных МРТ-модальностей;
- просматривать предсказанную маску и наложение маски на МРТ;
- анализировать метрики качества при наличии эталонной маски;
- экспортировать результаты для дальнейшего просмотра или документирования;
- использовать результат как вспомогательную информацию, но не как окончательное клиническое заключение.

### 4.2. Оператор

Оператор отвечает за загрузку исследований и подготовку входных данных.

Операции:

- зарегистрироваться и авторизоваться;
- загрузить комплект файлов МРТ;
- проверить автоматическое сопоставление модальностей;
- заполнить или отредактировать DICOM-метаданные пациента и исследования;
- отправить исследование на обработку;
- отследить технический статус обработки;
- повторить загрузку при ошибке формата или неполном комплекте данных;
- скачать DICOM ZIP или отправить DICOM-срезы в Orthanc.

### 4.3. Администратор

Администратор отвечает за техническую эксплуатацию стенда.

Операции:

- запускать сервисы через Docker Compose;
- настраивать переменные окружения backend, PostgreSQL, Kafka, S3 и Orthanc;
- контролировать состояние контейнеров;
- проверять журналы backend, worker, Kafka, PostgreSQL, Nginx и Orthanc;
- обновлять модельный артефакт;
- выполнять резервное копирование метаданных и артефактов;
- очищать тестовые данные;
- проводить регламентное тестирование после обновления версии.

## 5. Входные данные

### 5.1. NIfTI

Основной формат входа для инференса — NIfTI.

Обязательные файлы:

| Модальность | Назначение | Обязательность |
| --- | --- | --- |
| `t1` | T1-взвешенное МРТ | Да |
| `t1ce` | T1-взвешенное МРТ с контрастированием | Да |
| `t2` | T2-взвешенное МРТ | Да |
| `flair` | T2-FLAIR | Да |

Опциональный файл:

| Файл | Назначение | Обязательность |
| --- | --- | --- |
| `true_mask` | Эталонная маска для расчёта метрик | Нет |

Поддерживаемые расширения:

- `.nii`;
- `.nii.gz`.

Ограничения:

- один комплект должен относиться к одному исследованию;
- все обязательные модальности должны быть согласованы по пространственной форме и ориентации;
- при отсутствии эталонной маски сервис формирует только предсказанную маску и визуализации, без Dice/IoU-метрик относительно ground truth.

### 5.2. DICOM

DICOM используется в учебном проекте как формат интеграции с радиологическим контуром.

Поддерживаемые сценарии:

- заполнение DICOM-метаданных пациента и исследования в интерфейсе;
- конвертация выбранной NIfTI-модальности в набор DICOM-срезов;
- скачивание DICOM-срезов в ZIP-архиве;
- отправка DICOM-срезов в Orthanc через REST API.

Минимальный набор DICOM-метаданных:

| Поле | Назначение |
| --- | --- |
| `PatientID` | Идентификатор пациента |
| `PatientName` | Имя пациента или учебный псевдоним |
| `PatientBirthDate` | Дата рождения |
| `PatientSex` | Пол |
| `StudyInstanceUID` | Идентификатор исследования |
| `SeriesInstanceUID` | Идентификатор серии |
| `StudyDescription` | Описание исследования |
| `SeriesDescription` | Описание серии |
| `Modality` | Тип модальности |

## 6. Выходные данные

| Выход | Формат | Описание |
| --- | --- | --- |
| Предсказанная маска | NIfTI / внутренний артефакт | 3D-маска с классами опухолевых областей |
| Метрики | JSON / CSV | Dice, IoU/Jaccard и дополнительные метрики при наличии `true_mask` |
| PNG-срез маски | PNG | Изображение выбранного среза предсказанной маски |
| PNG overlay | PNG | Наложение маски на выбранную МРТ-модальность |
| DICOM ZIP | ZIP с DICOM-файлами | Экспорт выбранной NIfTI-модальности в DICOM-срезы |
| DICOM-экспорт в Orthanc | DICOM через Orthanc REST | Передача DICOM-срезов в локальный PACS-контур |
| Статус обработки | JSON / SSE | `uploading`, `queued`, `processing`, `completed`, `failed` |

## 7. Функциональные требования

### 7.1. Авторизация и пользователи

- Сервис должен поддерживать регистрацию пользователя.
- Сервис должен поддерживать вход пользователя по логину и паролю.
- Для защищённых операций должен использоваться JWT-токен.
- Пользователь должен видеть только собственные сканы.

### 7.2. Загрузка исследования

- Сервис должен принимать multipart-запрос с обязательными модальностями `t1`, `t1ce`, `t2`, `flair`.
- Сервис должен проверять наличие обязательных файлов.
- Сервис должен создавать запись исследования в PostgreSQL.
- Сервис должен сохранять временные файлы в staging-хранилище.
- Сервис должен ставить задачу сегментации в Kafka.

### 7.3. Асинхронная обработка

- Обработка должна выполняться отдельным worker-процессом.
- Worker должен читать задачи из Kafka.
- Worker должен переводить исследование в статус `processing`.
- Worker должен запускать инференс модели.
- Worker должен сохранять исходные файлы, маску, PNG и метрики в S3-совместимое хранилище.
- После успешной обработки статус должен становиться `completed`.
- При ошибке статус должен становиться `failed`, а причина ошибки должна сохраняться в логах.

### 7.4. Просмотр результатов

- Пользователь должен видеть список своих исследований.
- Пользователь должен видеть статус каждого исследования.
- Пользователь должен открыть карточку исследования.
- Пользователь должен получить метрики сегментации, если была загружена эталонная маска.
- Пользователь должен выбрать индекс среза и модальность для визуализации.
- Сервис должен возвращать PNG-срез маски и overlay-изображение.
- Интерфейс должен обновлять список исследований через SSE без ручного обновления страницы.

### 7.5. DICOM и Orthanc

- Пользователь должен иметь возможность заполнить DICOM-метаданные.
- Сервис должен конвертировать выбранную NIfTI-модальность в DICOM-срезы.
- Пользователь должен иметь возможность скачать ZIP-архив DICOM-срезов.
- Пользователь должен иметь возможность отправить DICOM-срезы в Orthanc.
- Сервис должен сохранять связь между внутренним `case_id` и DICOM-метаданными исследования.

### 7.6. Управление исследованиями

- Пользователь должен иметь возможность переименовать исследование.
- Пользователь должен иметь возможность удалить исследование.
- При удалении должны удаляться связанные файлы из объектного хранилища, если это поддерживается текущей конфигурацией.

## 8. Нефункциональные требования

| Категория | Требование |
| --- | --- |
| Производительность | Загрузка файлов и постановка задачи должны выполняться без ожидания окончания инференса |
| Асинхронность | Длительная сегментация должна выполняться в worker-контейнере |
| Масштабируемость | Worker может быть масштабирован горизонтально при увеличении числа задач |
| Надёжность | Ошибка обработки одного исследования не должна останавливать весь сервис |
| Наблюдаемость | Компоненты должны писать логи по ключевым операциям |
| Хранение | Метаданные хранятся в PostgreSQL, файлы — в S3-compatible storage |
| Безопасность | Защищённые endpoints требуют JWT |
| Интерфейс | Интерфейс должен поддерживать русский и английский язык |
| Развёртывание | Сервис должен запускаться через Docker Compose |
| Воспроизводимость | Версия модели и настройки инференса должны быть зафиксированы в паспорте модели |

## 9. Ограничения учебного MVP

- Сервис является учебным прототипом и не предназначен для постановки клинического диагноза.
- Входной инференс ориентирован на NIfTI-данные BraTS-подобного формата.
- DICOM-контур реализован как учебный экспорт и отправка в Orthanc, а не как промышленная интеграция с PACS/РИС.
- Возврат результата в PACS допускается в упрощённом виде: через DICOM-срезы, secondary capture или attached report в зависимости от дальнейшей реализации.
- Качество модели ограничено объёмом обучающих данных, вычислительными ресурсами и выбранной конфигурацией 3D U-Net.
- Для полноценной клинической эксплуатации требуются клинические испытания, валидация на внешней выборке, управление рисками и сертификация.

## 10. Критерии MVP

MVP считается готовым, если выполнены следующие условия:

| № | Критерий | Проверка |
| --- | --- | --- |
| 1 | Пользователь может зарегистрироваться и войти в систему | Успешный `POST /auth/register`, `POST /auth/login` |
| 2 | Пользователь может загрузить комплект `t1`, `t1ce`, `t2`, `flair` | Успешный `POST /predict` |
| 3 | После загрузки создаётся запись исследования | Запись появляется в `GET /scans` |
| 4 | Задача попадает в Kafka | Worker получает сообщение |
| 5 | Worker запускает сегментацию | Статус меняется на `processing` |
| 6 | Результат сохраняется | Статус меняется на `completed` |
| 7 | Пользователь видит метрики при наличии `true_mask` | Доступен endpoint метрик |
| 8 | Пользователь видит PNG-срез маски | Доступен endpoint PNG |
| 9 | Пользователь видит overlay маски на МРТ | Доступна визуализация overlay |
| 10 | Пользователь может скачать DICOM ZIP | Доступен endpoint DICOM-экспорта |
| 11 | Пользователь может отправить DICOM в Orthanc | Orthanc принимает экземпляры |
| 12 | Ошибка обработки отображается как `failed` | Некорректный файл приводит к управляемой ошибке |
| 13 | Все компоненты запускаются через Docker Compose | `docker compose up --build` поднимает стек |

## 11. Критерии качества результата

Для учебного MVP фиксируются следующие ориентиры:

| Метрика | Назначение | Ожидаемый уровень для учебного прототипа |
| --- | --- | --- |
| Mean Dice | Общая оценка совпадения маски | Должна быть рассчитана на тестовой выборке |
| Dice по классам | Оценка качества по областям опухоли | Должна быть рассчитана для каждого класса |
| IoU/Jaccard | Дополнительная метрика перекрытия | Должна быть рассчитана при наличии `true_mask` |
| Время обработки | Техническая оценка производительности | Должно быть зафиксировано в протоколе тестирования |
| Доля успешных обработок | Устойчивость pipeline | Все корректные тестовые кейсы должны завершаться `completed` |

## 12. Основной сценарий использования

1. Пользователь открывает веб-интерфейс.
2. Пользователь регистрируется или входит в систему.
3. Пользователь выбирает четыре NIfTI-файла: `t1`, `t1ce`, `t2`, `flair`.
4. При наличии эталонной маски пользователь добавляет `true_mask`.
5. Backend принимает файлы и создаёт запись исследования.
6. Backend ставит задачу в Kafka.
7. Worker запускает инференс.
8. Worker сохраняет маску, метрики и артефакты.
9. Frontend получает обновление статуса через SSE.
10. Пользователь открывает карточку исследования.
11. Пользователь просматривает метрики, PNG-срезы и overlay.
12. При необходимости пользователь выполняет DICOM-экспорт или отправку в Orthanc.

## 13. Исключительные сценарии

| Ситуация | Ожидаемое поведение |
| --- | --- |
| Не загружена одна из обязательных модальностей | Backend возвращает ошибку валидации |
| Загружен файл неподдерживаемого формата | Backend или worker переводит обработку в ошибку |
| Файлы разных размеров или несовместимой ориентации | Worker завершает задачу со статусом `failed` |
| Kafka недоступна | Backend не должен подтверждать постановку задачи как успешную |
| S3 недоступен | Worker фиксирует ошибку сохранения артефактов |
| Orthanc недоступен | DICOM-экспорт в Orthanc завершается ошибкой, но результаты сегментации остаются доступными |
| Пользователь запрашивает чужой скан | Backend возвращает отказ доступа |
